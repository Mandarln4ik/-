# NeuroForge

Android-приложение для Poco X8 Pro Max (Dimensity 9500s): инференс нейросетей на NPU,
диффузионная генерация изображений и апскейл до 4K — полностью на устройстве, без сервера.

---

## Коротко: что здесь честно работает, а что нет

| Заявка | Реальность |
|---|---|
| «Задействует NPU» | Да — через LiteRT NeuroPilot. Но **проверяется замером**, а не декларацией: приложение гоняет один и тот же граф на NPU/GPU/CPU и показывает медианы. |
| «Диффузия на NPU» | **Нет, и это осознанно.** Диффузионный трансформер с int4-весами и динамическим вниманием — не то, что ускоряет APU. Он идёт на CPU/XNNPACK. |
| «Текстовая модель на NPU» | Да, через LiteRT-LM. Причём `litert-community` публикует графы, **скомпилированные под конкретный ускоритель** — приложение читает `Build.SOC_MODEL` и на этом телефоне скачивает сборку `..._mt6991.litertlm`, а не общую. |
| «Генерация 4K» | Нативно 4K на телефоне не генерирует **никто** — внимание растёт квадратично по числу токенов. Здесь: генерация 512², затем ×4 super-resolution по тайлам → 4096². Вот **это** и есть работа для NPU. |

Главная инженерная мысль проекта: **NPU окупается на апскейлере, а не на генераторе.**
Свёрточная сеть с фиксированной формой входа и int8-весами — ровно то, что APU компилирует
один раз и потом прокручивает 25 раз подряд.

## Железо

| | |
|---|---|
| SoC | MediaTek Dimensity 9500s (3 нм) |
| CPU | 1× Cortex-X925 @ 3.73 ГГц, 3× Cortex-X4 @ 3.3 ГГц, 4× Cortex-A720 @ 2.4 ГГц |
| GPU | Arm Immortalis-G925 MC11 |
| NPU | MediaTek NPU 890 |
| Память | 12 ГБ LPDDR5X, UFS 4.1 |

### Что показало реальное устройство

На проверенном аппарате (Xiaomi, Android 16) `Build.SOC_MODEL` возвращает **MT6991** —
это Dimensity 9400, и он **есть** в списке поддержки LiteRT NeuroPilot
(MT6878 / MT6897 / MT6983 / MT6985 / MT6989 / MT6991).

Более того, приложение обнаружило, что **рантайм NeuroPilot уже установлен в системе**
(`Vendor runtime present: yes`) и виден узел `/dev/apusys`. То есть докладывать вручную
ничего не нужно — путь к APU открыт.

Остаётся последнее, что не выводится из этих признаков: возьмёт ли APU конкретный граф.
Поэтому экран **Device** разделяет три утверждения разной силы:

1. что за SoC — из `Build.SOC_MODEL`;
2. что говорит статический список LiteRT — `NpuCompatibilityChecker`;
3. **что реально запустилось** — по результатам бенчмарка.

Только третье — доказательство. Первые два регулярно расходятся с реальностью в обе стороны.

И четвёртое, отдельное от них: **что вообще опубликовано под этот чип**. Проверка каталога
в CI нашла в `litert-community/Gemma3-1B-IT` набор сборок вида `..._mt6989`, `..._mt6991`,
`..._sm8750`, `..._Google_Tensor_G5` — это графы, уже скомпилированные под один APU. SoC
устройства встаёт первым в список предпочтений при выборе файла, так что на MT6991 скачается
именно сборка MT6991. Репозиторий без таких вариантов от этого не меняется: несовпавшая
подсказка просто не добавляет кандидату очков.

Репозиторий Gemma закрыт лицензией Google — файл на месте, а загрузка отвечает 401. Это
чинится человеком в браузере, а не ретраем, поэтому в **Settings** есть поле для токена
Hugging Face, и сообщение об ошибке говорит, что именно нужно сделать. Qwen3 0.6B открыт.

## Как получается 4K

```
промпт ──▶ chat-шаблон ──▶ 256 id + маска ──▶ [ текстовый энкодер ] ──▶ эмбеддинги
                                                                            │
seed ──▶ шум (1024 × 128) ─────────────▶ [ DiT × 4 шага ] ◀──────────────────┘
                                                │
                              аффинное + распаковка патчей
                                                ▼
                                    (1, 32, 64, 64) ──▶ [ VAE ] ──▶ 512×512
                                                                      │
                                       ┌──────────────────────────────┘
                                       ▼
                       ресэмпл 1024² ──▶ [ ×4 SR, 25 тайлов на NPU ] ──▶ 4096×4096
```

Каждое число в этой цепочке взято из эталонной реализации модели, а не из соглашений её
семейства — контракт тензоров целиком расписан в [`docs/MODELS.md`](docs/MODELS.md).

Две стратегии, обе считаются заранее и показываются до запуска:

- **Fast** — один проход сети. 512² → ресэмпл ×2 → 1024² → ×4 → 4096². **25 тайлов.**
- **Quality** — без увеличения ресэмплом: 512² → ×4 → 2048² → ×4 → 8192² → вниз до 4096².
  Резче, но **~5× больше тайлов.**

Пиковая память аккумулятора на 4096² — 256 МиБ; приложение проверяет бюджет кучи **до**
аллокации и отказывается с внятным сообщением, а не падает в OOM внутри пиксельного цикла.

Швы между тайлами растушёвываются: перекрытие 32 px, линейные рампы, нормализация по сумме
весов. Это покрыто тестом, который прогоняет сетку с «сетью-тождеством» и проверяет, что
градиент восстанавливается точно — если это так, любой видимый шов идёт от сети, а не от сшивки.

## Модели

Подробности — [`docs/MODELS.md`](docs/MODELS.md). **Ни одна модель не требует компьютера:**
всё скачивается и запускается прямо в приложении.

| Стадия | Модель | Размер | Куда идёт |
|---|---|---|---|
| Смоук-тест | **MobileNetV3-Small**, int8 channelwise | ~4 МБ | **NPU** → GPU → CPU |
| Текст | Qwen3-4B (обрезанный), int4 | 1.7 ГиБ | CPU |
| Генератор | **Bonsai Image 4B** — тернарный DiT на архитектуре FLUX.2-klein-4B | 2.1 ГиБ | CPU/XNNPACK |
| VAE | декодер, fp32 | 0.2 ГиБ | GPU → CPU |
| Апскейл | **ESRGAN ×4**, int8-веса, тайл 128 px | 4 МБ | **NPU** → GPU → CPU |

### Апскейлер: параметры измерены, а не взяты из описания

| | |
|---|---|
| вход | `[1, 128, 128, 3]` float32 |
| выход | `[1, 512, 512, 3]` float32 |
| диапазон | **[0, 255]**, не [0, 1] |

На входе `[0, 1]` эта сеть возвращает значения примерно от −5 до 10 — шум, а не «картинка
похуже». Диапазон записан в каталоге и закреплён тестом.

Модель публикуется как `.tar.gz`; приложение скачивает, проверяет SHA-256 и распаковывает
на устройстве. При распаковке пропускаются AppleDouble-файлы (`._имя`) — у них то же
расширение, и поиск по `.tflite` достал бы resource fork вместо модели.

### Конвертация своих моделей — на самом телефоне

Внутри APK конвертера нет и быть не может: Android-приложение это песочница JVM, Python и
MLIR-компилятор в ней негде держать.

Но телефон — не только приложение. Через Termux поднимается Debian aarch64 на тех же
ARM64-ядрах, и **весь тулчейн под ARM64 существует** — проверено скачиванием пакетов:

| `torch` 2.14 | `manylinux_2_28_aarch64` |
|---|---|
| `tensorflow` 2.21 | `manylinux_2_27_aarch64` |
| `ai-edge-litert` 2.2 | `manylinux_2_27_aarch64` |
| `ai-edge-torch`, `ai-edge-quantizer` | чистый Python |

Никакой эмуляции. Инструкция — [`docs/ON_DEVICE_CONVERSION.md`](docs/ON_DEVICE_CONVERSION.md),
скрипты — [`tools/android/`](tools/android/).

Оговорка: доступность ARM64-пакетов проверена, **полный прогон конвертации на телефоне — нет**
(нет ARM64-устройства для теста). Упереться, скорее всего, может в память или время.

Моделям из каталога конвертация не нужна — они уже в формате LiteRT.

### AOT под NPU: дырка не там, где я думал

Я писал здесь, что скомпилировать модель под APU на самом телефоне нельзя. Это неверно как
утверждение о железе, и настоящая картина полезнее — подробности и как проверить в
[`docs/NPU_COMPILATION.md`](docs/NPU_COMPILATION.md).

Коротко: под aarch64 не собран **ни один** вендорный плагин компиляции в `ai-edge-litert`
2.2.0 — ни MediaTek, ни Qualcomm, ни Samsung, ни Google Tensor, ни Intel. Но в NeuroPilot
SDK у MediaTek ARM-сборка есть, и наборы экспортов у неё и у x86-компилятора **совпадают** —
по 104 символа `Neuron*`, из них 30 `NeuronCompilation_*`. То есть компилирующий API под ARM
есть; нет плагина LiteRT, который его зовёт.

Что с этим делать:

* **Сегодня** — [`.github/workflows/compile-npu.yml`](.github/workflows/compile-npu.yml).
  Раннер GitHub это и есть x86_64-машина с Linux: указываете модель и `MT6991`, забираете
  граф. Компьютер не нужен.
* **Чтобы закрыть по-настоящему** — [`docs/NPU_AARCH64_REQUEST.md`](docs/NPU_AARCH64_REQUEST.md),
  письмо в репозиторий LiteRT (а не в MediaTek — дырка там) с таблицами символов.

## Сборка

```bash
git clone <this repo> && cd -
./gradlew :app:assembleDebug        # нужен Android SDK (compileSdk 36), NDK и CMake
```

llama.cpp собирается из исходников (тег `b6100`) в `libllama_jni.so` — первая сборка
скачивает его и занимает несколько минут, дальше кэшируется. По умолчанию код компилируется
под `armv8.2-a+dotprod+fp16`: это самый широкий базис, на котором int8-ядра квантованных
матмулов всё ещё собираются в векторные инструкции, и он есть на любом arm64 с API 31.
На Dimensity 9500s быстрее с `i8mm`, но это уже armv8.6 — на более старых телефонах такой
APK упадёт с SIGILL, поэтому это ручной выбор:

```bash
./gradlew :app:assembleRelease -PllamaArmArch=armv9.2-a+i8mm+dotprod+fp16+sve2
```

Чистое ядро собирается и тестируется **без** Android SDK:

```bash
cd core && ./gradlew test           # 182 теста
```

Для NPU дополнительно нужны рантайм-библиотеки NeuroPilot —
см. [`docs/NPU_RUNTIME.md`](docs/NPU_RUNTIME.md). Без них приложение работает,
просто на GPU/CPU, и прямо об этом пишет на экране Device.

## Настройки ускорителя

Вкладка **Settings**, выбор сохраняется между запусками:

| Режим | Поведение |
|---|---|
| **Auto** | NPU → GPU → CPU, с откатом |
| **NPU only** | **Без отката.** Модель, которую APU не берёт, падает с причиной |
| **GPU → CPU** | Мимо NPU — для сравнения |
| **CPU only** | Базовая линия |

Режим «NPU only» — главный. Остальные откатываются молча, и именно поэтому «работает на NPU»
так часто ничего не значит: отличить граф, дошедший до APU, от тихо ушедшего на CPU нельзя.
Строгий режим отказывается откатываться — ответ однозначен даже когда он «нет».

## Бэкенды для текста

Вкладка **Settings**, выбор сохраняется между запусками и решает, какие модели показываются
во вкладке Models. Какой бэкенд *откроет* файл, решает расширение, а не настройка: `.gguf`
не откроется в LiteRT-LM, что ни выбери.

| Бэкенд | Формат | Доходит до APU |
|---|---|---|
| **LiteRT-LM** | `.litertlm` | **да** |
| ExecuTorch | `.pte` | нет |
| llama.cpp | `.gguf` | нет |

Это не рейтинг фреймворков, а свойство того, что реально лежит в APK — проверено
распаковкой артефактов, а не чтением документации:

* **ExecuTorch.** Вендорные бэкенды, включая MediaTek NeuroPilot, вкомпилированы в рантайм
  при его сборке. Публичный `org.pytorch:executorch-android` содержит XNNPACK и больше
  ничего — видно по символам в `jni/arm64-v8a`. Чтобы дотянуться до APU, AAR нужно собирать
  против NeuroPilot SDK; приложение этого сделать не может.
* **llama.cpp.** У него есть Vulkan и OpenCL под Android, но это опции времени сборки со
  своими оговорками по драйверам, и ни одна не запускалась на этом телефоне. Заявить GPU,
  не проверив, — ровно та же ошибка, ради которой существует бейдж ускорителя.

Смысл двух CPU-бэкендов не в скорости, а в том, что они читают форматы, которые LiteRT не
открывает. В GGUF опубликовано больше открытых моделей, чем во всех остальных мобильных
форматах вместе взятых. В каталоге есть пары из одних и тех же весов в разных форматах
(Gemma 3 1B и Qwen2.5 0.5B) — это единственный честный способ увидеть, что даёт APU:
модель должна быть та же самая.

## Вложения, зрение и инструменты

К сообщению можно приложить файл или фото. Пути расходятся, потому что у этих двух вещей
нет ничего общего.

| что приложено | куда уходит |
|---|---|
| фото | в рантайм **картинкой**, через модель со зрением |
| текст, код, лог, конфиг | в промпт, с бюджетом в токенах |
| PDF, архив, таблица | **отклоняется сразу**, в момент выбора, с именем файла |

Текстовые файлы обрамляются и подписываются, бюджет делится между ними поровну — иначе один
большой лог вытеснит маленький конфиг, ради которого вопрос и задавался. Обрезка не молчит:
модель, ответившая по половине файла, когда в ответе об этом ни слова, хуже модели, которая
скажет, что получила половину.

Файл копируется в хранилище приложения сразу. `content://` от пикера — временный доступ к
чужому документу, он умирает вместе с процессом, а чат открывают через неделю.

**Зрение — свойство весов, а не рантайма.** LiteRT-LM умеет нести vision-башню, но текстовая
сборка Gemma 3 1B на нём всё равно ничего не видит. Движок сначала просит vision-executor и,
если тот не стартует, откатывается на текст и говорит об этом. Фото модели без зрения
отклоняется с причиной — до загрузки, по каталогу, чтобы не ждать гигабайт ради отказа.
Единственная зрячая модель в каталоге — **Gemma 3n E2B**.

**Инструменты — настоящий function calling.** LiteRT-LM принимает описание в формате OpenAPI
и сам вызывает функцию, когда модель просит, вклеивая результат в тот же ответ.

| инструмент | зачем |
|---|---|
| `current_time` | часы устройства: представление модели о дате — это момент её обучения |
| `device_info` | телефон, чипсет и ускоритель, на котором инференс **реально** идёт |
| `calculate` | арифметика, в которой маленькие модели увереннее всего ошибаются |

Всё локальное: модель крутится на устройстве именно чтобы ничего не уходило наружу. Вызывать
умеет только LiteRT-LM — в настройках так и написано.

Системная инструкция редактируется, под полем показана её цена в токенах, и датчик контекста
считает ту инструкцию, которая в силе.

### Что проверяется автоматически

Нативный слой — единственный код здесь, который может убить процесс без Java-стектрейса,
и эмулятор в CI его не трогает: он x86_64, а APK собирается только под arm64. Поэтому
`app/src/test/native` собирает тот же `llama_jni.cpp` под хост и прогоняет его на настоящей
(крошечной и бессмысленной) GGUF-модели. Так нашлись две ошибки: исключение C++,
перелетавшее границу JNI, и `GGML_ASSERT` на промпте длиннее `n_batch` — оба приводили
к `abort()`.

```
  runtime/                  детекция NPU, обёртка CompiledModel, бенчмарк
    TextEngine.kt           общий интерфейс, маршрутизация по расширению файла
    LiteRtLmEngine.kt       .litertlm — единственный путь до APU
    ExecuTorchEngine.kt     .pte
    LlamaCppEngine.kt       .gguf, KV-кэш и шаблон чата из метаданных модели
    DeviceTools.kt          тела инструментов: часы, железо, арифметика
  cpp/                      llama_jni.cpp + CMake: сборка llama.cpp в APK
  models/                   докачиваемая загрузка весов с проверкой
    AttachmentStore.kt      копия приложенного файла, переживающая перезапуск
  imaging/                  Bitmap ↔ тензор, тайловый апскейлер

```

Почему ядро отдельным модулем: планировщики, тайлинг и упаковка латентов — это математика,
где ошибка не падает, а тихо портит картинку. Вынесенные из Android, они покрываются
обычными JUnit-тестами и гоняются за 20 секунд на любой машине.

## Приватность

Веса скачиваются с Hugging Face при первом запуске и остаются на устройстве.
Промпты и изображения никуда не отправляются — сети нет нигде, кроме загрузчика моделей.
